# 需求：我們要做什麼

<!-- meta:start -->
Part 5　Side project：部落格平台 API　·　單元 5-01　·　約 20 分鐘
<!-- meta:end -->

## 學完你會

- 看懂一份需求書的組成：目標、角色、使用者故事、功能需求、非功能需求、範圍外
- 把「做一個部落格平台」這種一句話，拆成可以實作、可以驗收的條目
- 知道這套課程最後要做出來的 side project 長什麼樣，之後每一課學的東西會用在哪裡

## 情境

[0-01](../00-overview/01-how-web-api-works.md) 的任務只有一句話：「做一個部落格平台的後端 API」。這句話沒辦法直接動工，因為：

- 「部落格平台」要有哪些功能？要不要留言、要不要登入？
- 「文章」有哪些欄位？標題可以空白嗎？
- 做到什麼程度算做完？

**需求（Requirements）** 就是把這些問題的答案寫下來。寫需求不是為了應付流程，而是：寫不出來的地方，就是你還沒想清楚的地方；寫出來之後，每一條都能在最後拿來驗收。

## 一份需求書有哪些部分

| 部分 | 回答什麼 | 寫法 |
|---|---|---|
| 背景與目標 | 為什麼要做、做出來要達成什麼 | 兩三句話 |
| 角色 | 誰會用這個系統 | 列出角色，每個角色一句話 |
| 使用者故事 | 每個角色想做什麼、為了什麼 | 「身為＿＿，我想要＿＿，這樣我就能＿＿」 |
| 功能需求 | 系統要能做到的事，一條一條編號 | `R1`、`R2`…，每條都要**能驗收** |
| 非功能需求 | 不是功能、但一定要滿足的事：格式、錯誤處理、效能、安全 | 條列 |
| 範圍外 | 這一版**不做**的事 | 條列，避免越做越多 |

> [!TIP]
> **怎樣的需求才「能驗收」**
>
> 一條需求要能寫出「怎麼測、預期結果是什麼」。「文章要有標題」不夠；「標題必填，最多 200 字，超過回 400」才能驗收。寫需求時腦中同時想著 [5-10 驗收](10-acceptance.md) 那張表。

## 部落格平台 API 的需求書

### 背景與目標

- 這是一個練習用的 side project，目標是做出一個**可以放上 GitHub 的 Web API**，用上整套課程學的 SQL、EF Core、LINQ、ASP.NET Core。
- 只做後端 API，用 JSON 溝通；前端不在範圍內（用 OpenAPI 介面或 `.http` 檔測試）。
- 資料模型沿用練習專案 EfCoreLab：部落格、頁首、作者、文章、標籤。

### 角色

| 角色 | 說明 |
|---|---|
| 作者 | 經營部落格的人：開部落格、發文章、整理標籤 |
| 讀者 | 瀏覽文章的人：看列表、看單篇、依標籤找文章 |

這一版沒有登入功能，所以 API 不分辨呼叫的人是誰；「角色」只是幫助我們想功能。

### 使用者故事

- 身為作者，我想要**建立自己的部落格並設定頁首**，這樣讀者打開時能看到部落格的名稱和介紹。
- 身為作者，我想要**發表、修改、刪除文章**，並替文章**加標籤**，這樣內容才能分類。
- 身為讀者，我想要**看某個部落格的文章列表，新的在前面、可以翻頁**，這樣不用一次載入所有文章。
- 身為讀者，我想要**依標籤找文章**，這樣能找到同一主題的所有文章。
- 身為讀者，我想要**看到每篇文章的作者和標籤**。
- 身為作者，我想要**知道每個部落格有幾篇文章、總共被看了幾次**。

### 功能需求

| 編號 | 需求 | 相關單元 |
|---|---|---|
| R1 | 可以**建立部落格**。部落格要有網址，**網址不可重複**；重複時回 `409 Conflict`。 | 3-07、4-06 |
| R2 | 部落格可以有**一份頁首設定**（標題必填，副標題選填），一個部落格最多一份。 | 3-10（一對一） |
| R3 | 可以**查詢部落格清單**和**單一部落格**（含頁首）；不存在回 `404`。 | 3-05、3-11 |
| R4 | 可以**修改**部落格的網址與評分、**刪除**部落格；刪除時底下的文章**一併刪除**。 | 3-07、3-16 |
| R5 | 可以在部落格底下**發表文章**。標題**必填、最多 200 字**；內容選填；發布時間沒給就用**現在時間**；可以指定作者，也可以沒有作者。 | 3-07、4-05 |
| R6 | 可以**修改、刪除**文章。 | 3-07 |
| R7 | 可以查某個部落格的**文章列表**：**新到舊**排序，支援**分頁**（`page`、`pageSize`，預設每頁 10 筆），每筆包含標題、發布時間、瀏覽數、作者名字、標籤名稱。 | 3-04、3-13 |
| R8 | 可以查**單篇文章**的完整內容（含作者、標籤、所屬部落格網址）；每查一次**瀏覽數加 1**。 | 3-05、3-07 |
| R9 | 文章可以有**多個標籤**，同一個標籤可以用在多篇文章；**標籤名稱不可重複**。新增或修改文章時可以同時給標籤名稱，**不存在的標籤自動建立**。 | 3-12、3-16 |
| R10 | 可以**依標籤名稱查文章**，新到舊排序。 | 3-12 |
| R11 | 可以查**作者清單**，每位作者附上**文章數**；沒寫過文章的作者也要列出（文章數 0）。 | 3-09、3-15 |
| R12 | 可以查**統計**：每個部落格的文章數與總瀏覽數。 | 3-09 |

### 非功能需求

| 編號 | 需求 | 相關單元 |
|---|---|---|
| N1 | 請求與回應一律用 **JSON**，屬性名稱用 camelCase（`publishedOn`）。 | 4-05 |
| N2 | 輸入不合法回 **400**，並說明哪個欄位錯；找不到回 **404**；違反唯一性回 **409**。錯誤格式統一用 **ProblemDetails**。 | 4-06 |
| N3 | API **不直接回傳 Entity**，一律回傳 DTO（只含需要的欄位）。 | 4-09 |
| N4 | 提供 **OpenAPI** 文件，開發環境可以在瀏覽器測試。 | 4-02、4-10 |
| N5 | 連線字串等設定放在 `appsettings.json` / User Secrets，**不把密碼 commit 進 git**。 | 4-08 |
| N6 | 開發環境可以在主控台看到 EF Core 送出的 SQL。 | 4-08 |
| N7 | 資料庫結構用 **Migration** 管理，clone 下來執行一個指令就能建好資料庫與範例資料。 | 5-04 |
| N8 | 用 **.NET 10**、EF Core 10、SQL Server（LocalDB）。 | — |

### 範圍外（這一版不做）

- 登入、權限（誰都可以呼叫任何 API）
- 留言、按讚
- 圖片上傳
- 全文搜尋
- 前端網頁

這些留到做完第一版、而且還想繼續的時候。

### 驗收條件（節錄）

每條功能需求都要能這樣寫；完整版在 [5-10](10-acceptance.md)。

| 需求 | 怎麼測 | 預期 |
|---|---|---|
| R1 | 用同一個網址 `POST /blogs` 兩次 | 第一次 `201`，第二次 `409` |
| R5 | `POST /blogs/1/posts`，標題給 201 個字 | `400`，錯誤訊息指出 `title` |
| R5 | `POST /blogs/1/posts`，不給 `publishedOn` | `201`，回傳的 `publishedOn` 是今天 |
| R7 | `GET /blogs/1/posts?page=2&pageSize=2` | 回第 3、4 新的文章 |
| R9 | 兩篇文章都給標籤 `efcore` | `Tags` 表只有一筆 `efcore` |
| R11 | `GET /authors` | 阿傑也在清單裡，`postCount` 是 0 |

## 動手

讀完上面的需求書，回答三個問題（寫在紙上或筆記裡就好）：

1. 哪幾條需求會用到「一對多」？哪幾條會用到「多對多」？
2. R8「每查一次瀏覽數加 1」是**讀取**還是**寫入**？對 API 的設計有什麼影響？
3. 如果主管臨時說「文章要能排程發布（指定未來時間才公開）」，這條需求該怎麼寫才能驗收？

<details>
<summary>看答案</summary>

1. 一對多：R4（部落格 → 文章）、R5、R7、R11（作者 → 文章）。多對多：R9、R10（文章 ↔ 標籤）。一對一：R2。
2. 它是一個 `GET`，但會**寫入**資料庫（`Views + 1`）。嚴格來說 GET 不該有副作用（[4-01](../04-web-api/01-http.md)），但「瀏覽數」這種統計通常被接受；設計時要注意它會讓單篇查詢多一次 `UPDATE`，之後學 AsNoTracking 時這支 API 不能用。
3. 例如：「文章可以設定 `publishedOn` 為未來時間；文章列表（R7）與依標籤查詢（R10）**只回傳 `publishedOn` ≤ 現在**的文章；單篇查詢（R8）若文章尚未到時間回 `404`。」每一句都能測。

</details>

## 常見的坑

> [!WARNING]
> **把實作寫進需求**
>
> 「用 EF Core 的 Include 取文章」不是需求，是實作。需求只說**要什麼結果**（列表要包含標籤名稱），怎麼做留給設計與實作，否則之後換做法時需求書就過時了。

> [!WARNING]
> **沒有「範圍外」**
>
> 沒寫清楚不做什麼，做到一半就會一直冒出「順便加個留言好了」。第一版做小、做完、能跑，比做大做不完有價值。

> [!WARNING]
> **需求無法驗收**
>
> 「系統要快」「介面要好用」沒辦法測。改成「列表 API 在 1,000 篇文章時 500 ms 內回應」才能驗收；驗不了的需求，做完也不知道有沒有做到。

## 小練習

**練習 1**　把 N2 的「輸入不合法回 400」拆成 R5 的三條驗收條件（標題空白、標題過長、`blogId` 不存在）。

<details>
<summary>看答案</summary>

| 怎麼測 | 預期 |
|---|---|
| `POST /blogs/1/posts`，`title` 為空字串 | `400`，訊息指出 `title` 必填 |
| `title` 給 201 個字 | `400`，訊息指出 `title` 最多 200 字 |
| `POST /blogs/999/posts`（部落格不存在） | `404` |

</details>

**練習 2**　R11「沒寫過文章的作者也要列出」這句話，為什麼要特別寫？如果沒寫會怎樣？

<details>
<summary>看答案</summary>

因為最直覺的查法（JOIN 作者和文章再分組）會**漏掉沒有文章的作者**。寫明之後，實作時就知道要用 LEFT JOIN（[1-08](../01-sql/08-left-join.md)、[3-16](../03-linq/16-join.md)），驗收時也會特別去看阿傑在不在。需求書裡這種「邊界情況」最值錢。

</details>
